# Notes

## Assumptions

The problem statement is incomplete on purpose, so these are the gaps I filled rather than invented requirements.

- **Runtimes.** Import mean 3 minutes ("seconds to several minutes"), export mean 30 minutes ("tens of minutes"), mean package 20 GB (stated range 10–40 GB). All sizing and every deadline follows from these; they are the first numbers I would replace with measurements.
- **Deadlines bound hangs, they do not enforce an SLO.** 15 minutes for imports and 120 minutes for exports are deliberately far above the slowest healthy job. A tight deadline fails valid work, which is the failure mode the current code already has.
- **Export packages are derived data, import JSON is not.** Packages can be regenerated, so a 14-day expiry is acceptable. Import JSON is the *input* to exports, so it keeps the full 90 days. If a customer contract requires 90-day package retention, the bill goes from ~$2,600 to ~$9,600 and that trade is theirs to make.
- **Consumers read packages in-region**, so S3 internet egress is ~zero. If not, egress becomes a top-three line item.
- **The converter wrapper surfaces exit codes.** `RunningConversion.completion` is `Promise<void>`, so the handler cannot see why a conversion failed. I assume the wrapper rejects with an error carrying `exitCode`; `src/errors.ts` defines that shape. A failure that arrives without one is treated as neither permanent nor transient — see below.
- **`kill()` terminates *and* reaps.** The handler awaits it and treats resolution as "the child is gone and its memory is back". A wrapper that only sends SIGTERM and returns would satisfy the type and break the guarantee.
- **Exports are not resumable.** A failed attempt restarts from zero. At 200 exports/day, resumability costs more to build and operate than the wasted compute it saves.
- **Jobs already exist in the table.** The exercise is evolving a service under load, so rows written before `version` existed are the default case, not an edge case; the conditional write accepts a missing version and the fake covers it.

## Interface changes and why

- `JobStore.put(job)` → `update(id, changes, expectedVersion)`, a conditional **partial** update where `null` means REMOVE. Two reasons. Without a conditional write there is no way to make "only one worker owns this job" true. And without a *partial* write, the first worker claim replaces the whole item and takes the idempotency-key attribute and the TTL attribute with it, which silently breaks re-submission and 90-day expiry; `test/handle.test.ts` now has a test that only passes if unowned attributes survive.
- `JobStore.get(id, { consistentRead })`. DynamoDB reads are eventually consistent by default, and a stale read loses the conditional claim and turns an ordinary delivery into a deferral. The API's read-for-polling can stay eventual; the worker's cannot.
- `Job` gained `kind` and `leaseExpiresAt`. `kind` chooses the deadline, the queue, and the task size; `leaseExpiresAt` is what lets a duplicate delivery distinguish "another worker is converting right now" from "the previous owner died".
- `QueueMessage.retry(visibleInSeconds)`. A released retry needs `ChangeMessageVisibility(0)` or it cannot come back before the queue's visibility timeout — 125 minutes for exports, which is longer than the alarm that pages on backlog age, so one ordinary transient retry would page my own on-call. A deferral behind a live lease wants the opposite: come back when the lease expires, not before, so it costs one receive instead of several.
- `Clock.timeout(ms): Promise<never>` → `timeout(ms): Deadline` with `{ expired, cancel() }`. The promise still only rejects, so the original contract holds. What was missing is cancellation — ten concurrent messages each holding an uncancelled 120-minute timer keep timers and closures alive for the life of the task — and a distinguishable rejection, so the handler can tell "deadline expired, kill the child" from "the converter failed on its own". `now()` was added for lease arithmetic.
- `handle(message, store, converter, clock)` → `handle(message, deps)`. Deadlines, the attempt budget, and telemetry have to be injected per environment.
- Added a `Telemetry` seam with a no-op default. Every branch is something an operator needs a count of, and the metric names in DESIGN.md §4 are these event names. In the deployed EMF writer, `kind` and `classification` are dimensions and everything else is a property: each unique dimension set is a separately billed custom metric, so `jobId` as a dimension would mint ~1,000 new metrics a day. The trade is that alarms cannot be per-image-tag; releases are compared by slicing the logs instead.

## What I did not fix, and why

Ordered by how much it bothers me.

1. **The visibility-timeout heartbeat.** The lease is only correct if the queue does not redeliver while its owner is still working. That needs the poll loop to call `ChangeMessageVisibility` on a timer, and the poll loop is out of scope here (the assignment gives the per-message handler only). The lease degrades safely without it — a duplicate is deferred, not duplicated — but the message churns. First thing I would write next.
2. **The sweeper exists only on paper, and its access pattern is a cost trap.** It is what makes "every job reaches a terminal state" true, and it is not written. Two specifics I want on the record: its predicate cannot be "no message in flight", because SQS exposes no per-message in-flight query — the implementable version is time-based, `lease + max visibility timeout` elapsed — and if it is implemented as a minute-by-minute `Scan` over 90 days of items it costs ~$122/month, more than every other control-plane line combined. It needs a sparse GSI on `leaseExpiresAt` over non-terminal jobs. The appendix cost table carries the Scan figure, not the index figure, because the index is not built.
3. **Terminal writes are not retried.** A throttled write after a completed 30-minute export now releases the lease and returns the message instead of stranding the job, but the result is still lost and the export is paid for twice. A bounded retry around the terminal write only is the cheap fix.
4. **Result objects are written by the converter, not by the handler.** The handler passes an `outputKey` and trusts that a resolved completion means the bytes are durably there. A converter that resolves before its multipart upload completes would let the handler publish a pointer to nothing. The real wrapper should return an ETag and size, or the handler should `HeadObject` before publishing.
5. **The export stages the zip on disk instead of streaming it.** Streaming the vendor's output to S3 via multipart roughly halves peak scratch, which would make two slots genuinely fit on one task and halve per-package compute. It is the structurally better answer to the sizing problem and it is a bigger change than v1 should carry.
6. **The 1-hour import drain target is arbitrary and too slow.** Slot-hours are conserved, so draining 2,400 imports in 15 minutes costs the same ~$7 and only pushes harder on the vCPU quota. Making a 3-minute job wait an hour is a 20× latency amplification that buys nothing; I sized to a round number rather than to a requirement.
7. **Orphans from a previous task generation are not swept.** `kill()` handles the process this handler started. A SIGKILLed task leaves the JVM to container teardown; a reaping `pid 1` is the operational answer, not handler code.
8. **The permanent/transient table has one entry.** Exit 2. Real converters have a richer vocabulary (corrupt media, unsupported schema version, disk full), and misclassifying "disk full" as permanent would fail valid jobs. I would build that table from a month of DLQ samples rather than guess it.
9. **No structured reason codes.** Callers get a stringified error truncated to 1 KB. A stable `reasonCode` enum is what other teams' backends actually want to branch on.
10. **No webhook or sweeper code, and no load test.** The concurrency argument in DESIGN.md §1 is arithmetic, not a measurement; before v1 I would run one onboarding-shaped burst against the real converters and watch memory high-water marks per slot.

### Tests I know are weaker than they look

- **The legacy suite pins a frozen copy.** It can never fail from a regression in the new code, and the new tests can never fail from a change to the old. It is executable documentation of the defects, not regression protection — which is why the README says to delete both files together.
- **"discards a slow attempt's result" simulates the competing writer with a direct store write** rather than a second `handle()`, so the interleaving is asserted rather than exercised. The genuinely concurrent test covers the claim-conflict path, not the lease path; together the coverage is adequate, separately neither is exactly the scenario the production observations describe.
- **`flush(8)` is a fixed microtask count.** Under-flushing would fail loudly rather than pass vacuously, so it is a smell rather than a bug.
- Untested: clock skew, and the release-plus-redelivery interaction end to end.

## Remaining risks in what I did write

- **The lease depends on wall clocks, and that is a cost risk, not a correctness risk.** I want to be precise about this because it is the objection I expect. Uniform skew is harmless: every worker compares a lease against the same offset that wrote it. Mixed skew costs money, not integrity: a worker whose clock lags writes a lease that correctly-clocked workers read as expired, so a duplicate can claim the next attempt and convert the same package concurrently — but the `version` condition still fences every write, so the loser's result is discarded with `job.stale_write_discarded` and the job ends at the correct attempt with the correct result. The honest cost is duplicate work and an inflated `attempt`, which shortens the real retry budget. It is not a path to two conflicting published results.
- **The attempt budget is shared between converter failures and infrastructure failures.** Three unlucky task recycles fail a valid job. Separate counters would fix it.
- **Deadline expiry counts as an attempt**, so a deadline configured too short burns all three attempts before failing. The `job.deadline_exceeded` alarm exists to catch that configuration error before customers do.
- **`maxReceiveCount` 10 is a guess.** It needs to exceed the worst realistic number of deferrals per job, and I have no production distribution for that. `job.lease_held` and `job.claim_conflict` are emitted precisely so the number can be set from data.

## How AI was used

This submission was produced by working with an AI coding agent throughout, so the honest answer is "for most of the typing". What matters is what was accepted, what was not, and what a second pass caught.

**What I asked for.** A first-pass reading of the starter handler against the workload facts and the production observations, with the bugs ranked; a draft of the design review section by section; the in-memory fakes and test scaffolding; the cost arithmetic laid out so I could check it. Then, separately, an adversarial review of the finished submission — "attack this the way a platform panel would, verify every AWS fact and every number independently" — which is where most of the corrections below came from.

**What I accepted.** The fakes and test scaffolding, which are mechanical. The structure of the handler's claim/publish flow. Keeping the original handler in-tree with characterization tests against it, which I think is the strongest thing in the repo: it makes "these tests would have failed before" runnable rather than asserted. Most of the unit prices, after checking them.

**What the review caught that I had missed.** These were real, and several were embarrassing in a useful way.

- **`maxReceiveCount` 3 re-introduced the bug the code repair removed.** I argued at length that `receiveCount` is the wrong retry counter because duplicate deliveries inflate it — and then set the redrive threshold equal to the attempt budget, so every deferral (live lease, lost claim, released retry) spent a receive without spending an attempt. The effective budget was 2, or 1 on a doubly-delivered message. Now 10, with the reasoning stated in DESIGN.md §2 item 1.
- **My headline cost saving was not expressible in S3.** Lifecycle filters take literal prefixes, so the `jobs/*/attempts/*` rule I built the whole §5 conclusion on would have matched nothing. Worse, as scoped it would have deleted the import JSON that exports read. Results are now keyed per kind, exports expire at 14 days and imports at 90, incomplete multipart uploads are aborted, and the corrected figure is ~$1,620 of S3 and ~$2,600 total, against the ~$1,331 and ~$2,100 I had.
- **`JobStore.put` was documented as `UpdateItem` and implemented as a whole-item replace**, and the fake blessed it, so the suite could not tell the difference. As `PutItem` the first claim would destroy the idempotency key and the TTL attribute; as `UpdateItem` with only `SET`, `leaseExpiresAt` would never be removed and every redelivery would defer for up to 121 minutes. The interface now expresses partial updates with explicit removal, and there is a test that fails unless unowned attributes survive.
- **No `try`/`catch` around the handler body at all.** Any throw from any seam escaped into the poll loop, leaving the job `running` under a live lease. Fixed, with two tests.
- **`version` had no migration story.** Existing rows have no `version`, so the condition would fail forever and those jobs could never be claimed — in an exercise explicitly about evolving a service under load.
- **Retry latency was floored by the visibility timeout**, so a transient export failure waited 125 minutes for its next attempt and reliably tripped my own backlog-age alarm. I had this in my not-done list filed as "a cost optimisation, not a correctness issue", and aimed at the wrong direction. It is a correctness issue and it is fixed.
- **Operational gaps I would have been asked about in the room:** no DLQ depth alarm, nothing watching the sweeper that makes my terminal-state guarantee true, no `IteratorAge` on the webhook stream, and a canary alarm that would have scored a total submission outage as healthy because a missing datapoint defaults to not-breaching.
- **The webhook design had a worse failure mode than the one it removed.** Deriving notifications from the committed transition is right, but delivering on the stream shard means one customer's failing endpoint blocks every other customer's notifications for up to the stream's 24-hour retention. The stream Lambda now only fans into a delivery queue, retries are bounded, and the on-failure destination is S3 — the only one that carries the payload rather than shard coordinates.
- **EMF cardinality.** `jobId` and image tag as *dimensions* would have minted roughly a thousand billable custom metrics a day.
- Smaller, all corrected: the scaling metric divides by zero at zero tasks and never scales out from zero; the slot formula returned 2 while the text said 1; SQS 14-day retention is the maximum, not the default; NAT is charged in both directions, so the counterfactual is ~$13,000 rather than ~$5,400; `leaseGraceMs` differed between the shipped config and the test fakes, so the shipped value was untested; ECR is regional, so DR needs image replication; DynamoDB TTL can lag 48 hours.

**What I rejected or did not take.**

- **Downsizing the export task to 1 vCPU.** The review is right that a 1-slot task running one single-threaded conversion has no obvious use for 2 vCPU, and that it would cut export compute 43%. I kept 2 vCPU because multipart upload threads, JVM GC, and zip throughput on a 40 GB package are not single-threaded work — but that is a hypothesis, so I wrote it down as one in appendix B rather than as a justification, and the first profiling run settles it.
- **Applying the 1.4× utilization factor to the onboarding evening.** The factor models idle tail and scale-from-zero lag across a month of bursty low volume. A four-hour saturated drain packs nearly perfectly, so applying it there would overstate the number. The inconsistency is deliberate.
- **S3 tiered pricing** ($8,287 versus $8,611 at the flat rate). It is 4% and it changes no conclusion, and the flat rate is easier to audit at the precision the section claims.
- **The suggestion that the lease is unsafe under clock skew** — which the reviewer also concluded is wrong, and tried to break. I am not conceding it; the argument is in "remaining risks" above.
- **Fixing everything.** The first plan repaired all seven original defects in one pass. The assignment asks for the smallest change addressing the one or two most urgent risks, so the repair stayed scoped and the rest went in this file. That judgement survived the review.
